# TLS証明書と認証局による信頼

## この文書の目的

この文書では、`curl -v`でHTTPS通信を観察したときに生じた、次の疑問を整理します。

- 証明書は何のためにあるのか
- `/etc/ssl/cert.pem`には何が入っているのか
- サーバー証明書、CA証明書、クライアント証明書は何が違うのか
- クライアントは接続先をどのように確認するのか
- 証明書を検証できない相手は、悪意のある相手なのか
- ルートCAと中間CAはどのようにつながるのか
- 自分で構築したサーバーやオンプレサーバーでも証明書を取得できるのか
- 社内サーバーを利用するとき、なぜクライアントへ証明書を配布することがあるのか

最初に結論を示すと、TLS証明書は主に次の確認に使われます。

> 接続先が、URLで指定したドメインを名乗る資格を持つ相手かを確認する。

証明書は、Webサイトの内容や運営者の善良さまで保証するものではありません。

---

## 1. HTTPS接続の全体像

`https://www.example.com/`へ接続するとき、概ね次の順序で処理されます。

```text
URLを解釈する
  ↓
ホスト名をIPアドレスへ名前解決する
  ↓
サーバーの443番ポートへTCP接続する
  ↓
TLSハンドシェイクを行う
  ├── TLSバージョンや暗号方式を決める
  ├── サーバー証明書を受け取る
  ├── 証明書を検証する
  └── 通信に使う鍵を確立する
  ↓
暗号化された接続上でHTTPリクエストを送る
  ↓
HTTPレスポンスを受け取る
```

ここでは、TCP接続に成功しただけでは、まだ接続相手が正しいとは確認できていません。

```text
TCP接続成功
  =
指定したIPアドレスと通信できる

証明書検証成功
  =
指定したドメインを名乗る資格を持つ相手だと確認できる
```

HTTPSでは、TLSによって主に次の性質を実現します。

| 性質 | 意味 |
|---|---|
| 認証 | 接続相手が、指定したドメインを名乗る資格を持つか確認する |
| 機密性 | 通信内容を第三者から読まれにくくする |
| 完全性 | 通信内容の改ざんを検出する |

証明書は主に認証で使われます。HTTP通信そのものは、TLSハンドシェイクで確立した一時的な共通鍵によって暗号化されます。

## 2. 証明書とは何か

証明書は、概ね次の対応関係を示す電子的な文書です。

```text
ドメイン名
    ↕
公開鍵
```

サーバー証明書には、主に次の情報が含まれます。

- 証明書の対象となるドメイン名
- 公開鍵
- 有効期間
- 証明書を発行した認証局
- 利用目的
- 発行元による電子署名

証明書自体と公開鍵は、秘密情報ではありません。サーバーは接続時に証明書をクライアントへ提示します。

一方、公開鍵に対応する秘密鍵はサーバーだけが保持します。秘密鍵は外部へ公開してはいけません。

```text
サーバー証明書
├── ドメイン名
├── 公開鍵
├── 有効期間
└── CAの署名

サーバー
└── 対応する秘密鍵
    ※公開しない
```

TLSハンドシェイクでは、サーバーは証明書を提示するだけでなく、対応する秘密鍵を持っていることも暗号的に証明します。

## 3. 認証局（CA）とは何か

CAはCertificate Authorityの略で、日本語では認証局と呼びます。

CAの役割は、証明書の申請者が対象ドメインを管理していることなどを確認し、公開鍵とドメイン名の対応関係に電子署名を付けることです。

```text
申請者
  │
  │ ドメインを管理していることを証明
  ↓
認証局（CA）
  │
  │ 証明書へ電子署名
  ↓
サーバー証明書
```

ここで「CAから承認された」という表現は、次の意味に限定されます。

> CAが定めた方法でドメインの管理権限などを確認し、そのドメインと公開鍵の対応関係へ署名した。

CAが次のことを保証しているわけではありません。

- Webサイトの内容が正しい
- サービスに脆弱性がない
- 運営者が善良である
- 詐欺やマルウェアが存在しない

攻撃者が自分で所有するドメインに正規の証明書を取得することもできます。その証明書は「接続先がそのドメインであること」は示しますが、「安全なWebサイトであること」は示しません。

## 4. ルートCA、中間CA、サーバー証明書

証明書は、通常、次のような階層で発行されます。

```text
ルートCA証明書
  │
  │ 中間CA証明書へ署名
  ↓
中間CA証明書
  │
  │ サーバー証明書へ署名
  ↓
サーバー証明書
```

### ルートCA

信頼の起点となるCAです。

ルートCA証明書は自己署名されています。ただし、自己署名されているから自動的に信頼されるわけではありません。OS、ブラウザ、curlなどの提供者が、審査やポリシーに基づいて信頼ストアへ登録することで信頼の起点になります。

ルートCAの秘密鍵が侵害された場合の影響は非常に大きいため、通常は厳重に保護され、日常的なサーバー証明書の発行には直接使用されません。

### 中間CA

ルートCAから署名を受け、実際のサーバー証明書を発行するCAです。

中間CAを挟むことで、ルートCAの秘密鍵を日常的な発行処理から分離できます。

### サーバー証明書

特定のサーバーやドメインのために発行される証明書です。末端証明書またはリーフ証明書とも呼ばれます。

```text
ルートCA
  └── 中間CA
      └── www.example.comのサーバー証明書
```

この署名のつながりを証明書チェーン、または信頼のチェーンと呼びます。

## 5. `/etc/ssl/cert.pem`とは何か

curlの出力に次のような表示がありました。

```text
* CAfile: /etc/ssl/cert.pem
* CApath: none
```

`/etc/ssl/cert.pem`は、curlがサーバー証明書を検証するときに利用するCA証明書の束です。CAバンドルや信頼ストアと呼ばれることもあります。

```text
/etc/ssl/cert.pem
├── 信頼するルートCA証明書
├── 信頼するルートCA証明書
├── 信頼するルートCA証明書
└── ...
```

これは「信頼できるWebサーバー名の一覧」ではありません。

```text
誤った理解
  cert.pemにwww.example.comが書いてあれば信頼する

正しい理解
  cert.pemに信頼するCA証明書がある
  ↓
  サーバー証明書の署名をたどる
  ↓
  信頼するCAまで到達できれば、信頼チェーンを構築できる
```

`CAfile`はクライアント側に存在するファイルですが、クライアント自身を証明する「クライアント証明書」ではありません。サーバーが提示した証明書を検証するための信頼情報です。

`CApath: none`は、このcurlの表示上、CA証明書を格納したディレクトリが別途指定されていないことを示します。エラーではありません。

## 6. サーバーは何を送り、クライアントは何を持つのか

通常のHTTPSでは、サーバーとクライアントが次のように証明書を保持します。

```text
サーバーが保持するもの
├── サーバー証明書
├── 中間CA証明書
└── サーバーの秘密鍵

クライアントが保持するもの
└── 信頼するルートCA証明書
    例：/etc/ssl/cert.pem
```

接続時、サーバーは通常、サーバー証明書と必要な中間CA証明書をクライアントへ送ります。

```text
クライアント                         サーバー
    │                                  │
    │ ─── TLS接続開始 ───────────────→ │
    │                                  │
    │ ←── サーバー証明書 ───────────── │
    │ ←── 中間CA証明書 ─────────────── │
    │                                  │
    │ 手元のルートCA証明書とつなぐ      │
```

ルートCA証明書は、通常サーバーから送る必要がありません。クライアントは、サーバーから送られたという理由だけでルートCAを信頼してはいけないためです。

```text
サーバーから送られた証明書
    +
クライアントが事前に信頼しているルートCA
    ↓
証明書チェーンを検証
```

## 7. クライアントが検証すること

クライアントは、サーバー証明書について主に次を確認します。

| 確認項目 | 確認する内容 |
|---|---|
| 証明書チェーン | 信頼済みルートCAまで署名をたどれるか |
| ホスト名 | URLのホスト名と証明書のSANが一致するか |
| 有効期間 | 現在時刻が証明書の有効期間内か |
| 署名 | 各証明書の署名が正しいか |
| 秘密鍵の所持 | サーバーが証明書の公開鍵に対応する秘密鍵を持っているか |
| 利用目的 | サーバー認証に利用できる証明書か |

例えば、信頼済みCAが `example.com`用に発行した証明書を `pokemon.co.jp`が提示しても、ホスト名が一致しないため検証に失敗します。

```text
アクセス先
  pokemon.co.jp

提示された証明書
  example.com

結果
  ホスト名不一致のため拒否
```

信頼済みCAから発行されていることだけでは不十分です。

## 8. 証明書を検証できない相手は悪意のある相手か

証明書を検証できなかった場合、クライアントが判断できるのは次のことです。

> 現在持っている信頼情報では、接続相手が指定したドメインの正しい相手だと確認できない。

「悪意のある相手だと確認できた」という意味ではありません。

検証失敗には、次のような原因があります。

- 自己署名証明書を使用している
- 社内のプライベートCAから発行されている
- クライアントに必要なルートCAが登録されていない
- サーバーが中間CA証明書を適切に送っていない
- 証明書の有効期限が切れている
- 証明書のドメイン名がアクセス先と一致しない
- サーバーの証明書設定を間違えている
- 通信の途中でなりすましや傍受が発生している

原因をその場で区別できないため、curlやブラウザは原則として接続を中止します。

```text
確認できない
  ≠
悪意があると確定した

確認できない
  =
安全な接続だと判断できないため、接続を続けるべきではない
```

## 9. `curl -v`の証明書関連表示

次は、`curl -v`で表示された主な行と意味の対応です。

TLS 1.3ハンドシェイクの時系列と各処理の詳細は、[`curl -v`で観察するTLS 1.3ハンドシェイク](tls-1.3-handshake-flow.md)にまとめています。

| 表示 | 意味 |
|---|---|
| `Host ... was resolved` | ホスト名から接続先アドレスを取得した |
| `Connected to ... port 443` | TCP接続に成功した |
| `ALPN: curl offers h2,http/1.1` | HTTP/2とHTTP/1.1を利用候補として提示した |
| `Client hello (1)` | curlからTLSの利用条件を提示した |
| `CAfile: /etc/ssl/cert.pem` | サーバー証明書の検証に使うCAバンドル |
| `Server hello (2)` | サーバーがTLSの利用条件を選択した |
| `Unknown (8)` | TLS 1.3のEncryptedExtensions。表示上の`Unknown`でありエラーではない |
| `Certificate (11)` | サーバーから証明書を受信した |
| `CERT verify (15)` | サーバーが対応する秘密鍵を持つことを証明した |
| `Finished (20)` | TLSハンドシェイクの内容を相互に確認した |
| `SSL connection using TLSv1.3 ...` | TLS接続が確立し、採用された方式が決まった |
| `subject` | 証明書の対象情報 |
| `start date` | 証明書が有効になる日時 |
| `expire date` | 証明書の有効期限 |
| `subjectAltName ... matched` | URLのホスト名が証明書の対象名と一致した |
| `issuer` | 証明書を発行したCA |
| `SSL certificate verify ok.` | curlによる証明書検証が成功した |
| `ALPN: server accepted h2` | サーバーがHTTP/2を選択した |

### `(304)`はHTTPステータスコードではない

次の `(304)`は、HTTPの `304 Not Modified`ではありません。

```text
* (304) (IN), TLS handshake, Server hello (2):
```

この表示では、TLSのバージョン値 `0x0304`が16進数の`304`として表示されています。後続の表示から、TLS 1.3であることを確認できます。

### `CERT verify`と`SSL certificate verify ok.`の違い

名前は似ていますが、意味が異なります。

```text
CERT verify (15)
  サーバーが、証明書に対応する秘密鍵を持つことを証明する

SSL certificate verify ok.
  curlが、証明書チェーン、ホスト名、有効期間などを検証した結果
```

## 10. 証明書の種類

### サーバー証明書

サーバーがクライアントへ提示し、サーバーのドメイン名と公開鍵の対応を示します。

```text
クライアント
    ← サーバー証明書 ── サーバー
```

通常のWebサイトへのHTTPS接続では、主にサーバー証明書を検証します。

### CA証明書

他の証明書へ署名し、その証明書を検証するために使われます。

クライアントの信頼ストアに入っているルートCA証明書や、サーバーから送られる中間CA証明書が該当します。

### クライアント証明書

クライアントがサーバーへ提示し、ユーザーや端末の身元を証明します。

```text
クライアント
    ── クライアント証明書 → サーバー
```

通常の公開Webサイトでは、クライアント証明書を使わないことが一般的です。

サーバーとクライアントが互いに証明書を提示する方式を、相互TLSまたはmTLSと呼びます。

```text
クライアント                         サーバー
    │ ←── サーバー証明書 ─────────── │
    │ ─── クライアント証明書 ──────→ │
    │                                │
    └────── 相互に身元を確認 ────────┘
```

## 11. 社内でクライアントへ証明書が配布される理由

社内でクライアントへ証明書ファイルが配布される場合、少なくとも2つの異なる目的が考えられます。

### 目的1：社内CAを信頼させる

社内サーバーがプライベートCAから発行された証明書を使っている場合、一般的なPCやブラウザはそのプライベートCAを知りません。

そのため、社内ルートCA証明書をクライアントへ配布し、信頼ストアへ登録します。

```text
社内ルートCA
  └── 社内中間CA
      └── 社内サーバー証明書

社員PC
  └── 社内ルートCA証明書を信頼ストアへ登録
```

この場合、配布されるCA証明書は「社員PC自身の身元を示す証明書」ではありません。

> 社員PCが社内サーバーの証明書を検証できるようにするための信頼情報

です。

### 目的2：クライアント自身を認証する

mTLS、社内VPN、端末認証などでは、社員や端末ごとのクライアント証明書が配布されることがあります。

```text
社員PC
  ├── クライアント証明書
  └── 対応する秘密鍵
      ↓
社内サーバーへ自分の身元を証明
```

この場合は「クライアントがサーバーを信頼するため」ではなく、「サーバーがクライアントを認証するため」の証明書です。

### 配布されたファイルを区別する

| 配布物 | 主な目的 | 秘密情報か |
|---|---|---|
| 社内ルートCA証明書 | クライアントが社内サーバーを検証する | 通常は秘密ではない |
| 中間CA証明書 | 証明書チェーンを構築する | 通常は秘密ではない |
| クライアント証明書 | サーバーがクライアントを認証する | 証明書自体は秘密ではない |
| クライアント秘密鍵 | クライアントが証明書の所有者だと証明する | 秘密情報 |

`.pem`、`.crt`、`.cer`などの拡張子だけでは、内容を完全には判断できません。`.p12`や`.pfx`には、証明書と秘密鍵がまとめて格納されている場合があります。

社内から証明書ファイルを受け取った場合は、次を確認する必要があります。

- これはCA証明書か、クライアント証明書か
- 秘密鍵が含まれているか
- どの信頼ストアまたはアプリケーションへ登録するのか
- ファイルやパスワードをどのように保護するのか

## 12. 自分で構築したサーバーの証明書を取得する

サーバーがクラウド上にあるか、オンプレ環境にあるかは、公開CAによる証明書発行の本質的な条件ではありません。

TLSとSSLの用語、証明書の有効期限、管理責任、自動更新の詳細は、[TLSとSSLの違い、サーバー証明書の管理と自動更新](tls-vs-ssl-and-certificate-renewal.md)にまとめています。

重要なのは次の点です。

- 証明書に記載するドメインを管理している
- CAが指定する方法でドメイン管理権限を証明できる
- 発行された証明書と秘密鍵をサーバーへ安全に設定できる
- 有効期限が切れる前に更新できる

### 公開サーバーの場合

例えば、オンプレサーバーを `app.example.com`として公開する場合は、次の流れになります。

```text
example.comを管理する
  ↓
app.example.comを用意する
  ↓
サーバーまたはACMEクライアントで秘密鍵を生成する
  ↓
公開CAへ証明書を申請する
  ↓
ドメイン管理権限を証明する
  ↓
サーバー証明書と中間CA証明書を受け取る
  ↓
証明書、証明書チェーン、秘密鍵をWebサーバーへ設定する
  ↓
期限前の更新を自動化する
```

公開CAとして、Let's Encryptなどを利用できます。ACME対応クライアントを利用すると、申請、検証、取得、更新を自動化できます。

### ドメイン管理権限の確認方法

代表的な方法にHTTP-01とDNS-01があります。

| 方法 | 確認方法 | 主な特徴 |
|---|---|---|
| HTTP-01 | 指定されたファイルをHTTPで公開する | 通常、CAから80番ポートへ到達できる必要がある |
| DNS-01 | 指定されたTXTレコードを公開DNSへ追加する | サーバー自体を公開せずに検証でき、ワイルドカードにも利用できる |

#### HTTP-01

```text
CA
  ↓ HTTPで確認
http://app.example.com/.well-known/acme-challenge/...
```

CAが指定された内容を取得できれば、申請者がWebサーバーを操作できると判断します。

#### DNS-01

```text
_acme-challenge.app.example.com
  TXT "CAから指定された値"
```

CAが公開DNSのTXTレコードを確認できれば、申請者がそのドメインのDNSを管理していると判断します。

DNS-01では、証明書を設定するオンプレサーバー自体がインターネットから到達可能でなくても、公開DNSを操作できれば証明書を取得できる場合があります。

## 13. 社内限定サーバーの選択肢

社内限定のオンプレサーバーでは、主に次の選択肢があります。

| 方法 | クライアント側の追加設定 | 主な用途 |
|---|---|---|
| 公開CAの証明書を使う | 通常不要 | 所有する公開ドメインを社内サーバーにも利用する |
| プライベートCAを使う | 社内ルートCAの配布が必要 | 組織管理下の端末・社内サービス |
| 自己署名証明書を使う | 証明書を個別に信頼させる必要がある | 小規模な検証・ローカル開発 |

### 公開CAを利用する

所有する公開ドメインのサブドメインを社内用に使用し、DNS-01などで管理権限を証明します。

```text
internal.example.com
```

公開ルートCAまでチェーンがつながるため、一般的なクライアントの信頼ストアをそのまま利用できます。

### プライベートCAを利用する

組織内に独自のルートCAと中間CAを構築し、社内サーバー用証明書を発行します。

```text
社内ルートCA
  └── 社内中間CA
      ├── 社内Webサーバー証明書
      ├── 社内API証明書
      └── 社内VPN証明書
```

社内ルートCAは一般のクライアントから信頼されていないため、組織が管理する端末へ配布します。

### 自己署名証明書を利用する

自己署名証明書は、自分自身の秘密鍵で署名した証明書です。

作成するだけでは、他のクライアントから信頼されません。利用するクライアントごとに明示的に信頼させる必要があります。

小規模なローカル開発では利用できますが、サーバーや端末が増えると管理が難しくなるため、組織内ではプライベートCAを利用する方が管理しやすい場合があります。

---

## 14. AWSとオンプレの違い

AWSを使っているだけで、すべてのサーバーへ証明書が自動設定されるわけではありません。

AWS Certificate Managerと統合されたサービスでは、証明書の発行、配置、更新の多くをAWSが管理できます。

例：

- Elastic Load Balancing
- CloudFront
- API Gateway

一方、EC2上で自分でWebサーバーを動かす場合や、オンプレサーバーを使う場合は、次のいずれかが必要です。

- ACMEクライアントで証明書を取得・更新する
- エクスポート可能な証明書を取得して配置する
- ロードバランサーやリバースプロキシでTLSを終端する
- プライベートCAを利用する

```text
AWSの管理サービス
  証明書管理を自動化しやすい

EC2・オンプレ
  証明書の取得、配置、更新を自分で設計する
```

信頼の仕組み自体は、クラウドでもオンプレでも同じです。

## 15. 信頼はクライアントごとに決まる

同じサーバー証明書でも、クライアントが持つ信頼ストアによって結果が変わることがあります。

```text
クライアントA
  社内ルートCAを登録済み
  → 社内サーバーを検証できる

クライアントB
  社内ルートCAを未登録
  → 社内サーバーを検証できない
```

したがって、「信頼される証明書」は絶対的に決まるのではなく、クライアントがどのルートCAを信頼しているかによって決まります。

一般公開サービスでは、主要なOSやブラウザがあらかじめ信頼している公開CAを利用します。社内サービスでは、組織が管理端末へ独自の信頼情報を配布できます。

## 16. セキュリティ上の注意

### 秘密鍵を配布・公開しない

サーバー秘密鍵やクライアント秘密鍵は、証明書の所有者であることを証明する重要な秘密情報です。

```text
暗号学上の秘密ではない
├── サーバー証明書
├── クライアント証明書
├── ルートCA証明書
└── 中間CA証明書

秘密として厳重に保護する
├── サーバー秘密鍵
├── クライアント秘密鍵
└── CA秘密鍵
```

証明書にはドメイン名、組織名、ユーザー名などの情報が含まれる場合があります。暗号学上の秘密ではなくても、組織の情報管理ポリシーに従って扱います。

### 証明書エラーを安易に無視しない

curlの`-k`または`--insecure`は、証明書検証を無効化します。

```bash
curl -k https://example.com/
```

検証用として挙動を確認する場合を除き、証明書エラーの解決方法として安易に使用してはいけません。証明書を検証できない状態では、接続相手が正しいことを確認できません。

### 有効期限と更新を管理する

証明書には有効期限があります。期限切れを防ぐため、ACMEなどによる自動更新と、更新失敗を検知する監視が必要です。

### CA証明書の配布経路を保護する

社内ルートCA証明書自体は通常秘密ではありませんが、誤ったCA証明書を信頼ストアへ追加すると、偽のサーバー証明書まで信頼する危険があります。

そのため、社内CA証明書は管理された方法で配布し、入手元とフィンガープリントなどを確認します。

## 17. 疑問への短い回答

### 証明書は、クライアントがサーバーとの安全な接続を確認するためのものか

概ね正しいです。より正確には、証明書によって「接続先が指定したドメインを名乗る資格を持つ相手か」を確認し、その確認を前提としてTLSの暗号化通信を確立します。

### `/etc/ssl/cert.pem`には信頼できるサーバーが記載されているのか

いいえ。信頼するCAの証明書が格納されています。サーバー名の一覧ではありません。

### CAfileはクライアント証明書なのか

いいえ。クライアント側にあるファイルですが、サーバー証明書を検証するためのCAバンドルです。

### サーバー側にも証明書があるのか

あります。通常のHTTPSでは、サーバーがサーバー証明書と中間CA証明書をクライアントへ提示します。

### 証明書に記載されていないサーバーは信頼できないのか

あるサーバー証明書は、そのSANに記載されたドメインに対してのみ有効です。ただし、別のサーバーは、そのサーバー用に発行された別の証明書を提示できます。

### 信頼済みCAへチェーンがつながらない相手は悪意があるのか

悪意があるとは断定できません。しかし、クライアントは正しい相手だと確認できないため、安全のため接続を中止します。

### オンプレサーバーでも公開CAの証明書を取得できるのか

できます。サーバーの設置場所ではなく、対象ドメインの管理権限をCAへ証明できるかが重要です。

### 社内でクライアントへ証明書が配布されるのはなぜか

主に次の2つの可能性があります。

1. 社内サーバーの証明書を検証できるよう、社内ルートCA証明書を配布する
2. 社員や端末をmTLSなどで認証するため、クライアント証明書と秘密鍵を配布する

この2つは目的が異なるため、配布された証明書がどちらなのか確認する必要があります。
