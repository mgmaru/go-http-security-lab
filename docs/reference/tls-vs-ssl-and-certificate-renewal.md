# TLSとSSLの違い、サーバー証明書の管理と自動更新

## この文書の目的

この文書では、次の疑問を整理します。

- TLSとSSLは何が違うのか
- `curl -v`が、TLS 1.3を使用しているのに`SSL connection`と表示するのはなぜか
- SSL証明書とTLS証明書は別のものなのか
- サーバー証明書になぜ有効期限があるのか
- 証明書は誰が管理・更新するのか
- 証明書の更新は何を行う処理なのか
- ACMEなどによって、どこまで自動化できるのか
- 自動更新を設定すれば、管理者は何もしなくてよいのか

最初に結論を示します。

```text
SSL
  現在は使用しない古いプロトコル

TLS
  SSLを引き継いだ現在の暗号化通信プロトコル

サーバー証明書
  TLSを終端する場所で管理する

証明書更新
  既存証明書の期限を延ばすのではなく、
  新しい証明書を取得して入れ替える

自動更新
  ACMEやクラウドの証明書管理サービスで実現できる

運用責任
  自動化後も監視と失敗時の対応が必要
```

---

## 1. SSLからTLSへの移行

SSLはSecure Sockets Layer、TLSはTransport Layer Securityの略です。

TLSは、SSLを基礎として標準化・改良された後継プロトコルです。

```text
SSL 2.0
  ↓
SSL 3.0
  ↓
TLS 1.0
  ↓
TLS 1.1
  ↓
TLS 1.2
  ↓
TLS 1.3
```

名称は変わっていますが、目的は一貫しています。

- 通信相手を認証する
- 通信内容を暗号化する
- 通信内容の改ざんを検出する

### 現在の位置付け

| バージョン | 現在の位置付け |
|---|---|
| SSL 2.0 | 使用しない |
| SSL 3.0 | 使用しない |
| TLS 1.0 | 非推奨 |
| TLS 1.1 | 非推奨 |
| TLS 1.2 | 現在も広く利用される |
| TLS 1.3 | 現在の新しいTLSバージョン |

SSL 3.0は安全上の問題から非推奨となり、TLS 1.0とTLS 1.1も現在は非推奨です。

したがって、現在のHTTPS通信について「SSL通信」と呼ぶことがあっても、実際のプロトコルは通常TLSです。

---

## 2. `SSL connection using TLSv1.3`の意味

`curl -v`では、次のように表示されました。

```text
* SSL connection using TLSv1.3 / AEAD-AES128-GCM-SHA256 / [blank] / UNDEF
```

この表示は矛盾していません。

```text
SSL connection
  SSL/TLS系の暗号化接続を指す、curlの歴史的な表現

using TLSv1.3
  実際に使用しているプロトコル
```

正確には、次の意味です。

> SSL/TLS系の暗号化接続として、TLS 1.3を使用した。

この通信でSSL 3.0が使用されているわけではありません。実際に使用されたバージョンは `TLSv1.3`です。

---

## 3. SSL証明書とTLS証明書

「SSL証明書」という名称は現在も製品名や一般用語として使われていますが、現在のHTTPSで使われるプロトコルはTLSです。

日常的には、次の言葉が同じサーバー証明書を指すことがあります。

- SSL証明書
- TLS証明書
- SSL/TLS証明書
- HTTPS証明書
- サーバー証明書

証明書は通常X.509形式であり、証明書そのものとTLSプロトコルのバージョンは別の概念です。

```text
サーバー証明書
  ドメイン名と公開鍵の対応を示す

TLS 1.2 / TLS 1.3
  証明書を利用して通信相手を認証し、
  暗号化通信を確立するプロトコル
```

証明書があるだけで、SSL 3.0やTLS 1.3のどちらを使うかが決まるわけではありません。TLSバージョンは、クライアントとサーバーのハンドシェイクで決まります。

## 4. サーバー証明書に有効期限がある理由

サーバー証明書には、利用を開始できる日時と有効期限があります。

```text
start date
  証明書が有効になる日時

expire date
  証明書が無効になる日時
```

有効期限を設ける主な理由は次のとおりです。

- 秘密鍵が漏えいした場合の影響期間を制限する
- ドメインの管理者が変わった可能性に対応する
- ドメイン管理権限を定期的に再確認する
- 古い暗号方式や証明書設定を長期間残さない
- 失効確認だけに依存しすぎない
- 証明書やCAのポリシー変更を反映しやすくする

証明書の有効期限が切れると、curlやブラウザは次の状態になります。

```text
証明書の署名は正しい
  +
ホスト名も一致する
  +
信頼済みCAまでつながる
  +
有効期限が切れている
  ↓
証明書検証失敗
```

ほかの検証項目が正しくても、有効期限切れの証明書は有効なサーバー証明書として扱われません。

## 5. 公開サーバー証明書の有効期間

この節の情報は、2026年7月27日時点の公開TLSサーバー証明書に関するものです。社内プライベートCAの証明書には、同じ規則がそのまま適用されるとは限りません。

CA/Browser Forumの現行要件では、公開TLSサーバー証明書の最大有効期間は次のように短縮されます。

| 発行日 | 最大有効期間 |
|---|---:|
| 2026年3月15日より前 | 398日 |
| 2026年3月15日以降、2027年3月15日より前 | 200日 |
| 2027年3月15日以降、2029年3月15日より前 | 100日 |
| 2029年3月15日以降 | 47日 |

今回観察した証明書は、約198日間有効です。

```text
開始：2026年6月12日
終了：2026年12月26日
```

これは、現在の最大有効期間である200日以内に収まっています。

有効期間が短くなるほど、手作業だけで期限切れを防ぐことは難しくなります。そのため、証明書管理は自動更新を前提とする方向へ進んでいます。

## 6. 誰が証明書を管理するのか

基本的には、TLS接続を終端する場所を管理している主体が、証明書を管理します。

### TLS終端とは

TLS終端は、クライアントとのTLS接続を受け付け、証明書を提示し、暗号化と復号を行う場所です。

```text
クライアント
  ↓ HTTPS
ロードバランサー
  ↓ HTTPまたはHTTPS
Goアプリケーション
```

この例でロードバランサーがサーバー証明書を提示する場合、TLS終端はロードバランサーです。

### 構成ごとの管理主体

| TLS終端 | 主な管理主体 |
|---|---|
| Goアプリケーション自身 | アプリケーション・サーバー管理者 |
| Nginx・Apache | Webサーバー管理者 |
| オンプレのロードバランサー | インフラ管理者 |
| AWS ALB・CloudFront | AWS Certificate ManagerとAWS利用者 |
| CDN・マネージドホスティング | サービス提供者と契約者 |
| Kubernetes Ingress | クラスター管理者と証明書管理ツール |

クラウドサービスを利用した場合でも、すべての責任が自動的にクラウド事業者へ移るわけではありません。

利用者には、少なくとも次の責任が残ります。

- 正しいドメイン名で証明書を申請する
- DNS検証などに必要な設定を維持する
- 自動更新の対象になっていることを確認する
- 更新失敗を監視する
- 不要になった証明書や漏えいした秘密鍵へ対応する

---

## 7. 証明書のライフサイクル

サーバー証明書には、取得して終わりではなく、継続的なライフサイクルがあります。

```text
秘密鍵を生成する
  ↓
証明書を申請する
  ↓
ドメイン管理権限を証明する
  ↓
CAから証明書を取得する
  ↓
TLS終端へ配置する
  ↓
証明書を使用する
  ↓
期限前に新しい証明書を取得する
  ↓
新しい証明書へ入れ替える
  ↓
期限と更新結果を監視する
```

秘密鍵が漏えいした場合は、通常の更新を待たずに次を行います。

```text
漏えいした証明書を失効させる
  ↓
新しい秘密鍵を生成する
  ↓
新しい証明書を取得する
  ↓
サーバーへ再配置する
```

---

## 8. 「更新」は有効期限を書き換える処理ではない

証明書の更新では、既存証明書の有効期限を書き換えません。

CAから新しい証明書を発行してもらい、古い証明書と入れ替えます。

```text
古い証明書
  有効期間：2026年6月〜2026年12月

        ↓ 更新

新しい証明書
  新しいシリアル番号
  新しい有効期間
  新しいCAの署名
```

更新処理には、少なくとも次の段階があります。

1. CAへ新しい証明書を申請する
2. 必要に応じてドメイン管理権限を再検証する
3. 新しい証明書と証明書チェーンを取得する
4. TLS終端へ配置する
5. Webサーバーやロードバランサーへ反映する
6. 実際に新しい証明書が提示されることを確認する

証明書を取得できても、サーバーへの配置や再読み込みに失敗すれば、古い証明書が提示され続ける可能性があります。

```text
証明書発行成功
  ≠
サーバーへの更新反映成功
```

## 9. ACMEによる自動化

ACMEはAutomatic Certificate Management Environmentの略です。

CAとサーバー側のACMEクライアントが通信し、主に次を自動化します。

- ドメイン管理権限の検証
- 証明書の申請
- 証明書の取得
- 証明書の更新
- 証明書の失効要求

```text
ACMEクライアント
  │
  │ 証明書を申請
  ↓
ACME対応CA
  │
  │ ドメイン管理権限の証明を要求
  ↓
ACMEクライアント
  │
  │ HTTPまたはDNSで証明
  ↓
ACME対応CA
  │
  │ 新しい証明書を発行
  ↓
ACMEクライアント
  │
  │ TLS終端へ配置・反映
  ↓
HTTPS接続で新しい証明書を使用
```

### 代表的なドメイン検証

| 方法 | 検証内容 |
|---|---|
| HTTP-01 | 指定URLでCAのトークンを公開できるか |
| DNS-01 | 指定されたDNS TXTレコードを作成できるか |

HTTP-01では、通常、CAから80番ポートへアクセスできる必要があります。

DNS-01では、DNS APIなどを利用してTXTレコードの作成と削除を自動化できます。サーバー自体を証明書発行時にインターネットへ公開しない構成でも利用できる場合があります。

## 10. 自動更新の代表例

### Certbot

Certbotは、Let's EncryptなどのACME対応CAから証明書を取得・更新するACMEクライアントです。

```text
systemd timerまたはcron
  ↓ 定期的に起動
Certbot
  ↓ 更新時期を確認
必要な証明書だけ更新
  ↓
Nginx・Apacheなどへ反映
```

代表的な更新コマンドは次です。

```bash
certbot renew
```

定期実行されても、毎回必ず新しい証明書を発行するわけではありません。更新対象となった証明書だけを処理します。

### Caddy

Caddyは、条件を満たすドメインについて、自動HTTPS機能により証明書の取得と更新を管理できます。

```text
ドメインを設定
  ↓
Caddyが証明書を取得
  ↓
HTTPSを有効化
  ↓
期限前に自動更新
```

Caddyのように、Webサーバー自身が証明書管理機能を持つ場合は、別の更新スクリプトを用意しなくてもよい構成にできます。

### Kubernetes

Kubernetesでは、cert-managerなどを使って証明書の申請、Secretへの格納、更新を自動化する構成があります。

ただし、証明書を更新した後にIngressやアプリケーションが新しい内容を正しく利用できるかも確認する必要があります。

### AWS Certificate Manager

AWS Certificate Manager（ACM）と、ALBやCloudFrontなどの統合サービスを利用すると、条件を満たすAmazon発行証明書について、AWSが更新と配置を管理できます。

```text
ACM
  ├── 証明書を発行
  ├── 更新条件を確認
  └── 統合サービスへ反映

ALB / CloudFront
  └── クライアントへ証明書を提示
```

ただし、すべての証明書がACMの自動更新対象になるわけではありません。

- AWSサービスとの関連付け状態
- 証明書の取得方法
- DNS検証の維持
- インポート証明書かどうか

などによって、自動更新の対象かどうかが変わります。

## 11. 公開CAとプライベートCAの自動更新

ACMEは公開CAだけの仕組みではありません。組織のプライベートCAがACMEに対応していれば、社内サーバー証明書の発行と更新も自動化できます。

```text
公開CA
  └── インターネットで広く信頼される証明書を発行

プライベートCA
  └── 組織内で信頼される証明書を発行
```

プライベートCAの場合は、自動更新とは別に、クライアントへ社内ルートCA証明書を安全に配布する必要があります。

```text
証明書の自動更新
  サーバー側の証明書ライフサイクル

社内ルートCAの配布
  クライアント側の信頼設定
```

この2つは別の管理対象です。

## 12. 自動更新でも失敗する可能性がある

自動更新を設定しても、次のような理由で失敗する可能性があります。

| 原因 | 起こること |
|---|---|
| DNS設定を変更した | ドメイン管理権限を検証できない |
| 80番ポートを閉じた | HTTP-01に失敗する |
| DNS APIの認証情報が失効した | DNS-01のTXTレコードを作成できない |
| ACMEクライアントが停止した | 更新処理そのものが実行されない |
| ファイル権限が変わった | 新しい証明書を配置できない |
| Webサーバーの再読み込みに失敗した | 古い証明書が提示され続ける |
| CAとの通信に失敗した | 新しい証明書を取得できない |
| レート制限に達した | 一時的に証明書を発行できない |
| システム時刻がずれている | 有効期間の判定や検証に失敗する |

そのため、必要なのは自動更新だけではありません。

```text
自動更新
  +
更新結果のログ
  +
証明書期限の監視
  +
失敗時の通知
  +
再試行
  +
定期的な動作確認
```

## 13. 更新タイミング

証明書は、有効期限の直前ではなく、十分な余裕を持って更新します。

```text
有効期限直前に初回更新
  ↓
更新失敗
  ↓
再試行する時間がない
  ↓
証明書期限切れ
```

Let's Encryptは、ACME Renewal Information（ARI）による推奨更新期間の確認を案内しています。

ARIを利用できない場合の補助的な基準として、証明書の残り期間が全有効期間の約3分の1になった時点での更新が推奨されています。

```text
90日証明書の例

発行
  ↓ 約60日使用
残り約30日
  ↓ 更新開始
期限
```

更新を早めに開始することで、CAやネットワークが一時的に利用できない場合でも再試行できます。

## 14. 管理者が確認すること

### 導入時

- [ ] TLSをどこで終端しているか特定した
- [ ] 証明書の管理主体を明確にした
- [ ] 証明書と秘密鍵の保存場所を把握した
- [ ] ドメイン検証方法を把握した
- [ ] 自動更新の仕組みを設定した
- [ ] 更新後の配置・再読み込み方法を確認した

### 定期確認

- [ ] 証明書の有効期限を監視している
- [ ] 自動更新処理が定期的に動いている
- [ ] 更新失敗を通知できる
- [ ] 外部から実際に提示される証明書を確認している
- [ ] DNS APIなどの認証情報が有効である
- [ ] 不要になった証明書と秘密鍵を整理している

### インシデント時

- [ ] 秘密鍵が漏えいした場合の失効手順がある
- [ ] 新しい秘密鍵と証明書へ交換できる
- [ ] 影響するTLS終端をすべて把握できる
- [ ] 証明書更新後に接続確認を行える

## 15. よくある誤解

### SSLとTLSは同時に使用しているのか

通常は違います。`SSL connection using TLSv1.3`では、実際に使用しているプロトコルはTLS 1.3です。`SSL connection`は歴史的な表現です。

### SSL証明書とTLS証明書を別々に用意するのか

通常は用意しません。現在「SSL証明書」と呼ばれているものも、実際にはTLSによるHTTPS通信で使用されるサーバー証明書です。

### 証明書を取得したら、有効期限まで何もしなくてよいのか

いいえ。期限前の更新、更新失敗の監視、秘密鍵の保護が必要です。

### 自動更新なら期限切れは絶対に起こらないのか

いいえ。DNS、認証情報、ファイル権限、更新ツール、サーバー再読み込みなどの問題で失敗する可能性があります。

### 証明書更新では有効期限だけが書き換わるのか

いいえ。CAから新しい証明書が発行され、古い証明書と交換されます。

### クラウドを使えば証明書管理はすべて不要になるのか

いいえ。管理作業の多くを委任できますが、ドメイン検証、自動更新の対象確認、期限監視、障害対応などの責任は残ります。

今回の `curl -v`では、次を確認できました。


