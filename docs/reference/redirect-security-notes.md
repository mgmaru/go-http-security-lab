# 第1部 基礎概念

## 1-1. 外部入力とは

**サーバのプロセスの外に一度出た値は、戻ってきた時点ですべて外部入力**である。
「ユーザーがフォームに打ち込んだ文字」だけを外部入力だと考えると、大量に漏れる。

| 値 | 外部入力か | 理由 |
|---|---|---|
| フォームの入力欄 | ✅ | 言うまでもない |
| URLのクエリパラメータ | ✅ | 誰でも書き換えられる |
| hiddenフィールド | ✅ | 開発者ツールから編集可能。**見えない≠安全** |
| Cookie | ✅ | ブラウザ側で編集可能 |
| `Referer` ヘッダ | ✅ | 送信側が自由に設定できる |
| `Host` ヘッダ | ✅ | 同上。これでURLを組み立てると危険 |
| 自分が発行したJWT | ✅ | 署名を検証するまでは中身を信じられない |
| 外部APIのレスポンス | ✅ | 相手が侵害されている可能性がある |
| コードに書いた固定文字列 | ❌ | プロセス外に出ていない |
| DBから引いた自サーバ管理の値 | ❌ | ただし書き込み経路が外部入力なら要注意 |

> **判定基準**：その値は一度サーバの外に出たか？
> 出たなら外部入力。**自分が10分前に発行した値でも同じ。**

## 1-2. リダイレクトとは

サーバがブラウザに「そのページではなく、こちらへ行け」と指示する仕組み。

```
ブラウザ「/settings ください」
    ↓
サーバ「そこは今ダメ。/login へ行って」（リダイレクト指示）
    ↓
ブラウザが自動で /login へ移動
```

ユーザーは何も操作していないのに画面が切り替わる。ログイン誘導、URL変更後の転送、
決済サービスへの遷移など、あちこちで使われるごく普通の機能。

## 1-3. オープンリダイレクトとは

リダイレクトの**行き先を、サイトの外から自由に指定できてしまう状態**。
「オープン＝誰でも、どこへでも指定し放題」の意味。

```
https://example.com/login?next=https://evil.com
                              ↑ ここに何を書いても、その通りに飛ばしてくれる
```

**例え話**：受付に「この人が言った場所へ案内してください」とだけ書かれた張り紙がある状態。
受付は正規の建物の正規の受付なのに、案内先の妥当性を誰も確認していない。
だから攻撃者は「では倉庫の裏へ」と言える。

### 重要な性質

- **サイト自体は壊れていない。** データも盗まれないし、侵入されるわけでもない
- ただ「この正規サイトは、頼めばどこへでも人を送り届けてくれる」という性質があるだけ
- **単体では低〜中リスク。他の攻撃と組み合わさると致命的**になる（第3部）

### どういうコードがそうなるか

```
next の値を受け取る
    ↓
その値へリダイレクトする   ← 何のチェックもない
```

開発者に悪意も手抜きの自覚もない。「ログイン後に元のページへ戻す」つもりで書いており、
`next` に外部サイトのURLが入る可能性を考えていないだけ。**だから頻繁に発生する。**

## 1-4. 中核となる3つの原則

### 原則A：境界で1回だけパースし、以降は構造化された値だけを使う

いわゆる *parse, don't validate*。

```
[外から来た文字列]
      │
      ▼ 入口で1回だけパース ← ここでしか文字列を扱わない
[構造化された値]
      │
      ├─→ 検証もこの値で
      └─→ 実際の処理もこの値で   ← 文字列に戻さない
```

事故の多くは「文字列のまま持ち回って各所で部分一致を書く」か
「検証と使用で別々にパースする」のどちらか。

### 原則B：表現できる範囲を、必要な範囲まで狭める

```
必要な範囲 ─┐
            ├─ このギャップが脆弱性の正体
表現できる範囲 ─┘
```

例：要件は「自サイト内のページを指定したい」なのに、
形式として「世界中のどのサイトでも指定できるURL」を選んでしまった → オープンリダイレクト。

### 原則C：対策には優先順位がある

```
① そもそも外部入力を行き先に混ぜない  ← 最善
② 混ぜる範囲を最小にする（パスだけ等）
③ 検証する                          ← 最後の手段
```

> **検証が要る設計は、既に一段負けている。**
> 「検証が必要だ」と判断した時点で、まず①に戻れないか考える。

## 1-5. 値を見るときの2つの問い

危険の種類を取り違えないための整理。

| | 秘密の値（トークン等） | 指示の値（リダイレクト先等） |
|---|---|---|
| 値の性質 | 他人に知られてはいけない | 知られても困らない |
| 何が問題か | **漏れる** | **書き換えられる** |
| 誰が困るか | 知られた本人 | その値を信じて動くサーバ |
| 対策の軸 | URLに置かない・短命化・使い捨て | 表現範囲を絞る・検証する |

> **毎回問うべき2つ**
> 1. この値は**秘密か**？ → 漏れる経路（履歴・ログ・Referer）を塞ぐ
> 2. この値は**書き換えられたらどうなるか**？ → 表現範囲を絞る

# 第2部 比較の原則 — 文字列一致 vs 構造化比較

最初の問い「オブジェクト一致は文字列一致よりセキュリティ的に良いか」への回答。

**結論：多くの場面で構造化比較の方が安全。ただし「オブジェクトだから安全」なのではなく、
安全になる理由がはっきりしていて、それが崩れる条件もある。**

## 2-1. 構造化比較が有利な3つの理由

### 理由1：表現の揺れを一度だけ吸収できる

同じ意味を持つ文字列は無数にある。

| 届いた値 | 意味 | 文字列一致の結果 |
|---|---|---|
| `https://EXAMPLE.com` | 同じサイト | ✗ 不一致（ホスト名は本来大小無視） |
| `https://example.com:443` | 同じサイト | ✗ 不一致（443はhttpsの既定ポート） |
| `https://example.com/` | 同じサイト | ✗ 不一致（末尾スラッシュ） |

パースすれば `{scheme, host, port}` に分解され、この揺れはパーサが吸収する。

> ⚠️ **危険な連鎖**：不一致が多いので開発者が「緩く判定しよう」と `contains` や
> `startsWith` に逃げる。これが理由2の事故につながる。

### 理由2：部分一致の誤用を構造的に防げる

**実際に最も多い事故。** 文字列比較の事故のほとんどは完全一致ではなく部分一致。

| 実装 | 攻撃者の入力 | なぜ通るか |
|---|---|---|
| `origin.startsWith("https://example.com")` | `https://example.com.evil.com` | `evil.com` のサブドメイン＝攻撃者の持ち物 |
| `host.endsWith("example.com")` | `notexample.com` | 攻撃者が取得できるドメイン |
| `path.contains("../")` を弾く | `..%2f..%2fetc%2fpasswd` | `/` をエンコード。後段でデコードされる |
| 同上 | `....//` | 先頭の `../` が1回除去されると `../` に戻る |

構造化すれば「ホスト部だけを完全一致」で比べられ、この手の判定を書く必要がなくなる。

### 理由3：種類の取り違えを型が止める

```
func canDelete(userID string, role string) bool

canDelete(role, userID)   // ← 引数を入れ替えても、コンパイルは通る
```

権限判定が「常にfalse」ならまだ気づくが、「常にtrue」側に転ぶと本番まで残る。

```
type UserID string
type Role   string

func canDelete(userID UserID, role Role) bool   // 入れ替えるとコンパイルエラー
```

中身は同じ文字列だが、**別の種類の値であることを型が覚えている。**

## 2-2. 構造化しても安全にならない4つのケース

### ケース1：パーサが2つあると意味がない（parser differential）

```
u = parse(next)                  // ①検証のためにパースする
if u.host != "example.com" { 拒否 }
redirect(next)                   // ②元の「文字列」をそのまま使う ← ここが致命的
```

```
   受け取った文字列
        │
        ├──→ 自分のパーサ ──→ ホストは example.com → OK
        │
        └──→ ブラウザのパーサ ──→ ホストは evil.com → 実際はここへ飛ぶ
```

**検証したのはパース結果なのに、実際に使ったのは元の文字列。**
文字列は使う側でもう一度パースされ、解釈が少しでも違えば判定は無意味になる。

| 入力例 | 何が起きるか |
|---|---|
| `https://example.com\@evil.com` | バックスラッシュの扱いが割れ、ホストの解釈が変わる |
| `//evil.com` | 片方は「ホストなし」、ブラウザは `evil.com` と解釈 |

同じ構図はHTTPにもある（リクエストスマグリング）。原因はどちらも
**同じ文字列を2箇所で別々にパースしたこと。**

> **鉄則**：パースして検証に使ったオブジェクトを、そのまま組み立て直して使う。
> **文字列に戻して再パースさせない。**

### ケース2：深い等価比較そのものの落とし穴

- **JavaScript**：オブジェクトの `===` は参照比較。中身が同じでも常に `false`
  ```js
  {host: "example.com"} === {host: "example.com"}   // false
  ```
  権限判定に使うと、正規ユーザーを弾くか、`!==` 側が常に成立して全通過する
- **Go**：ポインタのフィールドが混じると「指す先が同じか」で比較される。
  また比較対象外のつもりの項目（作成日時・内部キャッシュ）が追加されると判定が突然壊れる

> **対策**：比較用のメソッドを定義し、**どのフィールドで一致とみなすかを明示する。**

### ケース3：秘密情報の比較は論点が別（タイミング攻撃）

```
if receivedToken == correctToken { 許可 }
```

一般的な文字列比較は、違いが見つかった時点で打ち切る。
つまり**先頭が合っているほど処理時間がわずかに長い。**
攻撃者は1文字目を総当たりし、最も遅かったものを採用し、2文字目へ……と進める。

- 正解は構造化ではなく**定数時間比較**（Go なら `crypto/subtle.ConstantTimeCompare`）
- むしろ「フィールドを1つずつ比べて違ったら返す」構造化比較は、
  どこまで合っていたかを時間差で漏らす方向に働く

### ケース4：オブジェクトをJSON文字列にして比べる＝文字列一致に逆戻り

JSONは同じ意味のデータに複数の書き方を許す。

| 送信側 | 受信側 |
|---|---|
| `{"a":1,"b":2}` | `{"b":2,"a":1}`（キー順） |
| `{"a": 1}` | `{"a":1}`（空白） |
| `{"a":1.0}` | `{"a":1}`（数値表現） |

署名検証で使うと、正規の要求が弾かれる。逆に重複キー `{"role":"user","role":"admin"}` の
扱いがライブラリごとに違えば、検証側は `user`、処理側は `admin` を読む（ケース1と同じ構図）。

> 構造化されたデータを扱っているつもりでも、**比較直前に文字列へ戻した時点で
> 理由1の「表現の揺れ」問題がそっくり戻ってくる。**
> だから正規化仕様（JCSなど）がわざわざ存在する。

## 2-3. 第2部のまとめ

- オブジェクト一致が安全なのではない。**原則A（境界で1回パース）を守った結果、
  自然にオブジェクト一致になる**
- 崩れる条件：パーサが2つある / 比較対象が不明瞭 / 秘密の比較 / 文字列に戻す

# 第3部 脅威 — オープンリダイレクトで何が起きるか

## 3-0. 前提：Cookieは漏れない

Cookieには「どのドメインに送るか」がひも付いている。

```
example.com のCookie
  └─ example.com へのリクエスト → 付く
  └─ evil.com   へのリクエスト → 付かない
```

ブラウザが強制する仕組み（同一オリジンポリシー）なので、リダイレクトで飛ばされても変わらない。
**セッションCookieが攻撃者に渡ることはない。**

> ただし **URLに載っている情報は漏れる**（3-3）。

## 3-1. フィッシング（これが主目的）

最大の用途は、**フィッシングリンクを本物に見せかけること。**

```
https://example.com/login?next=https://evil.com/login
   ↑ 正真正銘、本物のドメイン
```

```
① メールのリンク → 本物の example.com のログイン画面
                    （証明書も正規、アドレスバーも正しい。疑いようがない）
② ログイン成功
③ evil.com へリダイレクト
④ 「セッションが切れました。再度ログインしてください」
   → ここで入力したIDとパスワードが攻撃者の手に
```

被害者の体感は「ログインし直しただけ」。ドメインが変わったことに気づく人はほとんどいない。

> **なぜ効くのか**：フィッシング対策の教育がほぼ例外なく
> 「**リンク先のドメインを確認しましょう**」だから。
> オープンリダイレクトは、その唯一の防衛線を無効化する。
> メールのセキュリティフィルタもドメイン評価で判定するものが多く、正規ドメインなので通過する。

**Cookieを盗む必要はなく、パスワードそのものを本人に入力させる**のがポイント。

## 3-2. OAuth 認可コードの横取り（最も深刻）

OAuthでは、認証後に「認可コード」がURLパラメータとして戻り先に付いてくる。
戻り先は事前登録したものしか使えないが、**登録済みドメインにオープンリダイレクトがあると
そこを踏み台にできる。**

```
戻り先として登録:  https://example.com/callback
攻撃者が指定:      https://example.com/callback?next=https://evil.com
                        ↑ ドメインは登録済みなので検査を通過
                   ↓
認可コード付きで /callback に戻る
                   ↓
オープンリダイレクトで evil.com へ。code もURLに付いたまま運ばれる
                   ↓
攻撃者がそのコードでアクセストークンを取得 → アカウント乗っ取り
```

ここでは実質的に認証情報が攻撃者に渡る。経路はCookieではなく**URLパラメータ。**

### 対策（多層防御）

| 対策 | 内容 |
|---|---|
| **redirect_uri を完全一致で登録** | `https://example.com/*` や `/callback*` のような前方一致・ワイルドカードを使わない。完全一致なら `?next=` を付けた時点で弾かれる。**最も効く** |
| **PKCE を使う** | 認可コードを盗まれても、それだけではトークンに交換できなくする。現在は種別を問わず必須の推奨事項 |
| **state を検証** | CSRF対策。予測不能な値をセッションに保存し、戻り値と照合 |
| **コードは使い捨て・短命** | 二度目の使用を検知したら発行済みトークンを失効させる |

**PKCE の仕組み**

```
① アプリが乱数を生成し、そのハッシュを認証開始時に送る
② 認可コードを受け取る
③ トークン交換時に、元の乱数を提示する
④ 認可サーバがハッシュを照合。合わなければ拒否
```

乱数はアプリの手元にしかないので、コードだけ盗んだ攻撃者は④を通れない。

## 3-3. Referer 経由のトークン漏洩

ブラウザは遷移時に遷移元URLを `Referer` ヘッダで送ることがある。
遷移元URLに秘密が含まれていると、それが `evil.com` のログに残る。

```
example.com/reset?token=abc123 から evil.com へリダイレクト
       ↓
evil.com のログに「遷移元: .../reset?token=abc123」が残る
```

> **重要**：これは開発者が「Referer経由で送る」ことを選んでいるのではない。
> **ブラウザが勝手に送る。** 悪いのはRefererではなく、**URLに秘密を置いた設計**の方。

### 現在のブラウザの既定（`strict-origin-when-cross-origin`）

| 遷移 | 送られる内容 |
|---|---|
| 同一オリジン内 | フルURL（パス・クエリ含む） |
| 別オリジンへ（https→https） | **オリジンのみ**（`https://example.com`） |
| https → http | 何も送らない |

つまり `?token=abc123` は既定では外部に漏れない。さらに `Referrer-Policy: no-referrer` で完全に止められる。

### それでも「URLに秘密を置かない」が原則

Refererを塞いでも、他の経路が残る。

- ブラウザの履歴に残る（共用PC）
- サーバのアクセスログに平文で記録される（長期保存・閲覧権限も広い）
- プロキシやCDNのログ
- 肩越しに見られる / スクショに写る / チャットにURLを貼って共有される

**例外：パスワードリセットのリンク**
メールのリンクをクリックさせる以外に手段がないという制約から来る例外。
だから被害を小さくする対策を重ねる。

- 有効期限を短く（15分〜1時間）
- **一度使ったら即無効化**（使い捨て）
- 使用時にIPやUser-Agentの急変を検知
- `Referrer-Policy: no-referrer` を付ける
- リセット完了を本人にメール通知

> 「漏れない設計にする」が第一。無理なら「**漏れても短時間しか使えない**」に落とす。

## 3-4. その他の踏み台利用

| 攻撃 | 内容 |
|---|---|
| 多段リダイレクトの隠れ蓑 | マルウェア配布への誘導を正規ドメイン始まりにして検知を回避 |
| 許可リストの回避 | 「example.com なら通してよい」と判断する箇所を、外部への抜け穴にする |
| **`javascript:` スキーム** | `next=javascript:...` が通る実装だと、リダイレクトではなく**そのサイト上でスクリプトが実行される**（XSSに昇格）。この場合はCookieも盗まれる |

## 3-5. 脅威の一覧

| 脅威 | 何が漏れるか | 深刻度 |
|---|---|---|
| フィッシング | 本人が入力した認証情報 | 高（主目的） |
| OAuth認可コード横取り | URLパラメータ上のコード | 高 |
| Referer経由のトークン漏洩 | URLに載っていた秘密 | 中（既定では緩和済み） |
| `javascript:` によるXSS | Cookie含む何でも | 高（ただし別種の脆弱性） |

> **性質のまとめ**：オープンリダイレクト単体は「ブラウザの防御を突破する」種類の脆弱性ではない。
> **人間の判断（ドメインを見る）を欺く**、あるいは**他の脆弱性の威力を高める**もの。
> ブラウザの仕組みがCookieを守ってくれるので、**攻撃者は人間を狙う。**

---

# 第4部 実装パターン — リダイレクト先の受け取り方

## 4-0. 前提：`?next=` の値は誰が作っているか

```
① ユーザーが /settings にアクセス（まだ未ログイン）
       ↓
② サーバ「ログインが必要。でも後で /settings に戻したい」
       ↓
③ サーバが /login?next=○○ へリダイレクト  ← ★この○○を作るのはサーバ
       ↓
④ ユーザーがログインフォームに入力・送信
       ↓
⑤ サーバ「ログイン成功。next の値を見て戻り先を決めよう」
       ↓
⑥ ○○ から戻り先を決めてリダイレクト
```

- **③で何を入れるかはこちらの自由。** フルURLを入れる必然性はどこにもない
- **ただし⑤で受け取る値は信用できない。** 攻撃者は `/login?next=https://evil.com` という
  リンクを自分で作り、被害者にメールで送れる（③を経由せず④から始められる）

> 「自分で作った値だから安全」ではなく、
> 「**自分で作れる形式にしておいて、それ以外は全部捨てる**」という設計にする。

## 4-1. 第1候補：識別子で受け取る（最善）

### ③で入れる値

URLでもパスでもなく、**こちらが決めた短い名前。**

```
/login?next=settings
/login?next=dashboard
/login?next=billing
```

この `settings` はURLの一部ではない。単なる「行き先の名前」。

### ⑥での処理

サーバ側に**対応表**を持っておく（ソースコードに直接書く。外部入力から生成しない）。

```
"dashboard" → "/dashboard"
"settings"  → "/settings"
"billing"   → "/billing/overview"
```

```
受け取った next の値で、対応表を引く
  ├─ 表に載っていた → その行き先へリダイレクト
  └─ 表になかった   → 既定のページ（/ など）へリダイレクト
```

### 変換の向き

```
❌ URL → 識別子（そんな処理は存在しない）
✅ 識別子 → パス
```

- 識別子を**作る**のは③（ログイン画面へ送り出すとき）
- 識別子を**パスに戻す**のは⑥（ログイン成功時）。対応表を引くだけ

### なぜ安全か

```
next の値 = "https://evil.com"
       ↓
対応表を検索 → 該当なし
       ↓
/ へリダイレクト（攻撃失敗）
```

**受け取った文字列が一度もURLの材料になっていない。**
リダイレクト先は `"/settings"` のようにコード中の固定文字列そのもの。
外部入力とURL組み立てが完全に切り離されているので、パーサの解釈違いが起きる余地がない。

> これが「検証が要らない設計」の意味。
> **危険な入力を頑張って見抜くのではなく、危険な入力が入り込む場所を消している。**

### 制約

行き先が有限個で列挙できる場合にしか使えない。
「記事ページに戻す」のように無数にある場合は第2候補の方が素直。

## 4-2. 第2候補：相対パスで受け取る

### ③で入れる値

最初から**パス部分だけ**。ホストもスキームも含めない。

```
/login?next=/settings
/login?next=/articles/1234?tab=comments
```

### ⑥での検証

| 条件 | 通す例 | 弾く例 |
|---|---|---|
| `/` で始まる | `/settings` | `settings`、`https://evil.com` |
| 2文字目が `/` や `\` でない | `/settings` | `//evil.com`、`/\evil.com` |
| スキームやホストを含まない | `/settings` | `https://evil.com/x` |

**2文字目チェックの理由**
`//evil.com` は「スキーム相対URL」という正式な書き方で、ブラウザは現在のスキームを補って
`https://evil.com` と解釈する。`/` で始まるので素朴なチェックは通るが、行き先は外部サイト。
`/\evil.com` もブラウザによってはバックスラッシュをスラッシュ扱いする。

> 自分で文字を数えるより、**URLライブラリでパースして
> 「スキームが空」「ホストが空」「パスが `/` で始まる」を確認する**方が確実。

### ⑥での組み立て

```
"https://example.com"  ← 固定値。外部入力は一切混ざらない
        +
"/settings"            ← 検証済みの入力
```

**ホストは入力側から取らない。** 仮にパスの解釈に多少の揺れがあっても、
飛び先のドメインが自サイト以外になることはない。

### ⚠️ 「取り除く」ではなく「拒否する」

```
❌ スキームやホストが含まれていたら削る
✅ スキームやホストが含まれていたら拒否する
```

「危険な部分を削る」発想は `....//` と同じ罠にはまる。
削った結果また危険な形になる、削り漏れる、削る順序で結果が変わる……と考慮事項が無限に増える。
**「条件を満たさないものは受け付けない」の方が判断がシンプルで穴が空きにくい。**

## 4-3. 第3候補：フルURLで受け取る（外部遷移が要件の場合のみ）

決済サービスから戻る等でどうしても外部URLを扱う場合。

```
u = parse(input)
scheme が https でなければ拒否            ← javascript: や data: を弾く
host が許可リストに完全一致しなければ拒否   ← 部分一致は絶対に使わない
userinfo（@より前）があれば拒否 or 除去
fragment を除去

行き先 = 許可リストに登録済みの scheme + host + port
        + u から取り出した path / query
```

- 肝は最後の行。**scheme・host・portは「許可リスト側に書いてある値」を使い、入力側から取らない**
- `userinfo` に触れる理由：`https://evil.com@example.com` はホストが正しく `example.com` なので
  許可リスト検査を通るが、そのまま文字列化すると `@` より前が残り、アドレスバーの見え方が変わる

> **検証していないフィールドを素通しにしない。**

## 4-4. 別解：URLに載せずセッションに保存

```
② サーバがセッションに「戻り先: /settings」と記録
③ /login へリダイレクト（パラメータなし）
⑥ セッションから戻り先を取り出す
```

攻撃者は書き換えられないので、リンクを送りつける攻撃自体が成立しない。

**ただし万能ではない**

| 不便な点 | 内容 |
|---|---|
| タブを複数開くと壊れる | Aのタブで `/settings`、Bのタブで `/billing` からログインすると記録が上書きされる |
| サーバに状態が必要 | 複数台構成だと、どの台でも同じ記録が読める仕組みが要る |
| リンクとして共有できない | 「このリンクからログインして」と渡せない |

URL方式には**状態をサーバに持たなくてよく、リンクとして完結する**という利点がある。
だから広く使われ続けている。要件次第でどちらを選んでもよい。

## 4-5. 使い分け

| | 受け取る値 | 検証の必要性 | 適する場面 |
|---|---|---|---|
| 第1候補（識別子） | `settings` | **不要** | 戻り先が数個〜数十個 |
| 第2候補（相対パス） | `/articles/1234` | 少し必要 | 自サイト内なら任意のページ |
| 第3候補（フルURL） | `https://...` | 大量に必要 | 外部サービスへの遷移が要件 |
| 別解（セッション） | URLに載せない | 不要 | 状態を持てる構成、単一タブ前提 |

> 下に行くほど柔軟だが、検証すべきことが増える。**要件が許す限り上を選ぶ。**

## 疑問1：`redirect(u)` とオブジェクトを渡せばよいのか

**当初の仮説**
> リダイレクト関数にパース前の文字列を渡しているのが問題。パース後のオブジェクトを渡せばよいのでは。

**判定：方向性は正しい。ただし理由の理解が足りない。**

リダイレクトは最終的にHTTPの `Location` ヘッダになる。ヘッダは文字列なので、
**どこかで必ず文字列に戻る。** `redirect(u)` と書いても内部で文字列化されるだけ。

重要なのは、その文字列が

- ❌ ユーザーから受け取った元の文字列
- ✅ 検証済みオブジェクトを**シリアライズし直した**文字列

のどちらか。

```
❌ 元の文字列を使う
   input ──parse──→ u（検証OK）
     └──────────────────────→ Location  ← ブラウザが元の文字列を再解釈

✅ オブジェクトから作り直す
   input ──parse──→ u（検証OK） ──serialize──→ Location
                                              ↑ 正規化済み・曖昧さなし
```

`parse → serialize → parse` で同じ結果に戻ることは、まともなURLライブラリが保証している性質。

**`redirect(u)` が良い書き方である理由**は「オブジェクトだから安全」ではなく、
**関数の引数を文字列にしないことで、元の文字列を渡す経路を型で塞げる**から（第2部・理由3と同じ話）。

---

## 疑問2：識別子案とは、URLを識別子に変換すること？

**当初の仮説**
> URLを識別子に変換して、それを検証する？ どこで変換するのか？

**判定：誤解。変換の向きが逆。**

```
❌ URL → 識別子           （そんな処理は存在しない）
✅ 識別子 → パス（対応表）
```

**そもそも最初からURLを受け取らない。** `?next=` に入れるのは `settings` のような
こちらが決めた名前であり、URLではない。だから「URLを変換する」場面自体が存在しない。

| いつ | 何をするか |
|---|---|
| ③ ログイン画面へ送り出すとき | サーバが行き先に**名前を付けて**埋め込む |
| ⑥ ログイン成功時 | 対応表を引いて**名前をパスに戻す** |

**なぜ間違えやすいか**：「検証」という言葉に引きずられ、
「危険な入力をどう安全にするか」という枠で考えてしまった。
実際は**危険な入力が発生する場所そのものを消している**ので、変換も検証も存在しない。

---

## 疑問3：相対パス案とは、スキーム・ホストを取り除くこと？

**当初の仮説**
> 最初にスキームやホストを検証して、それを取り除いて、相対パスで処理する？

**判定：誤解。取り除くのではなく、含まれていたら拒否する。**

```
❌ 削る（サニタイズ）  → 削った結果また危険な形になる、削り漏れる、順序で結果が変わる
✅ 拒否する（バリデーション） → 判断がシンプルで穴が空きにくい
```

「危険な部分を削る」発想は、第2部で見た `....//` と同じ罠。
先頭の `../` を1回削ると残りが `../` に戻る、というのがまさに「削る」失敗例。

**正しい理解**
- 外部から受け取る値の**責任範囲をパスだけに限定する**
- スキームとホストは**自分が持っている固定値**を使う
- 入力にスキームやホストが含まれていたら、それは想定外なので**丸ごと拒否**

---

## 疑問4：オープンリダイレクトでCookieが漏れるのでは？

**当初の仮説**
> ログイン成功時にブラウザが持つCookieを悪意あるサイトに送ってしまうのでは？

**判定：誤り。ただし発想の方向は正しい。**

Cookieはドメインにひも付いており、`evil.com` へのリクエストには `evil.com` のCookieしか付かない。
ブラウザが強制する仕組みなので、リダイレクトで飛ばされても変わらない。

**実際の脅威**（第3部に詳述）

| | 狙われるもの |
|---|---|
| フィッシング | **人間の判断**。本人にパスワードを入力させる |
| OAuth横取り | **URLパラメータ**上の認可コード |
| Referer漏洩 | **URL上の秘密**（既定では緩和済み） |
| `javascript:` | この場合は**Cookieも盗まれる**（＝仮説が現実になるケース） |

**なぜ間違えやすいか**：「情報が漏れる」という直感自体は当たっている。
ただし漏れるのは**Cookieではなく、URLに載っている値**。
「ブラウザが何を守ってくれて、何を守ってくれないか」の線引きを持っておくと整理しやすい。

> ブラウザの仕組みがCookieを守るので、**攻撃者は人間を狙う。**

---

## 疑問5：Referer経由は設計としてよくないのでは？

**当初の仮説**
> セキュリティ的に危ない気がする。なぜRefererヘッダ経由をする必要があるのか？
> Refererを使わないと実装できないユースケースがあるのか？

**判定：危ないという直感は正しい。ただし前提に誤解がある。**

**開発者が「Referer経由でトークンを送る」ことを選んでいるのではない。ブラウザが勝手に送る。**

```
ページ: https://example.com/reset?token=abc123
   ↓ このページ内の画像・スクリプト・リンクへのリクエスト
Referer: https://example.com/reset?token=abc123  ← ブラウザが自動で付ける
```

つまり「Referer経由が必要か」ではなく、
「**URLにトークンを置いたせいで、ブラウザの既存の仕組みが勝手に漏らしてしまう**」という構図。

**Refererが存在する理由**（1990年代からある古い仕組み）

- リンク切れの発見（どのページから404に来たか）
- アクセス解析（流入元）
- 直リンク防止（画像の無断利用対策）
- CSRF対策の補助

ウェブが「文書をリンクでつなぐもの」だった時代の機能で、
**URLに秘密情報が載る時代は想定されていなかった。**

**業界も同じ結論に至っている**：現在は既定で情報量が絞られており（3-3参照）、
`Referrer-Policy: no-referrer` で完全に止められる。

---

## 疑問6：OAuth横取りも識別子案で防げるのでは？

**当初の仮説**
> これはかなり深刻。第一候補の識別子で行うことで防げそう。

**判定：正しい。ただし適用範囲に注意。**

登場する場所は2つある。

```
[A] OAuthの redirect_uri  ← 認可サーバに登録する戻り先
[B] 自社サイト内の next    ← ログイン後にどのページへ戻すか

redirect_uri = https://example.com/callback?next=https://evil.com
                └──[A] 登録済み──┘└────[B]の脆弱性────┘
```

認可サーバは[A]だけを見て「登録済みだ、OK」と判断する。
攻撃が成立していたのは、**[A]として登録されたページに[B]の脆弱性があった**から。

[B]を識別子方式にすれば踏み台が消える。**ただし対象は `/callback` だけではない。**
攻撃者は `redirect_uri=https://example.com/どこか?next=...` と指定できるので、
**サイト内のどこか1箇所にでもオープンリダイレクトが残っていれば、そこが使われる。**

> 対策は「callbackを直す」ではなく「**サイト全体からオープンリダイレクトを根絶する**」。
> 共通のリダイレクト処理を1箇所にまとめ、そこを通さないとリダイレクトできない構造にするのが現実的。

加えて、アプリ側のミスがあっても被害が出ないよう、OAuth側でも防ぐ（3-2の表）。

---

## 疑問7：`?next=` という設計自体が良くないのでは？

**当初の仮説**
> URLにトークンを置く設計が良くなかったように、リダイレクト先をURLで指定する構造も良くない気がする。

**判定：半分正しい。ただし2つは別の理由で危ない。**

| | URLにトークンを置く | URLにリダイレクト先を置く |
|---|---|---|
| 値の性質 | **秘密** | 公開情報 |
| 何が問題か | **漏れる** | **書き換えられる** |
| 教訓 | 秘密をURLに置くな | 外から来る値は書き換えられる前提で扱え |

`next=/settings` は見られても困らない。問題は書き換えられること。

**URLに置くこと自体が禁物なのではない**

```
/articles?page=3&sort=new
```

これらも書き換えられる（`page=-1` など）が、URLに置くのをやめるのではなく
サーバ側で検証することで対処する。`next` も同じ扱いでよい。

**本当にまずかったのは何か**

`next` の値を **URLという形式で受け取ったこと。**

```
要件:   自サイト内のページを指定したい
形式:   世界中のどのサイトでも指定できるURL
        ↑ このギャップが脆弱性の正体（原則B）
```

第1候補・第2候補は、`?next=` というパターンはそのまま使い、**値の形式だけを変えている。**

---

## 疑問8：ページ遷移時には必ず検証を挟むべきでは？

**当初の仮説**
> ページ遷移が起こる際には、必ず検証を挟む必要があるのが正しい気がする。

**判定：芯は正しいが、この形で覚えると危険。**

### 問題1：検証は「最後の砦」であって「第一手」ではない

第1候補には検証が存在しない（対応表を引くだけ）。
「必ず検証を挟む」と考えると、**最も安全な選択肢が視界から消える。**

### 問題2：「検証した」で安心してしまう

```
u = parse(next)
if u.host != "example.com" { 拒否 }   ← 検証は挟んでいる
redirect(next)                        ← でも元の文字列を使っている
```

- `startsWith("https://example.com")` → 検証を挟んでいるが `example.com.evil.com` が通る
- `contains("../")` を弾く → 検証を挟んでいるが `..%2f` が通る

**検証の有無ではなく、検証の中身と、検証した値をそのまま使っているかが問題。**
「必ず検証を挟む」というルールは、これらを全部「合格」にしてしまう。

### 正しい言い換え

> **外部から来た値が行き先を決めるなら、その値が指しうる範囲を、必要な範囲まで狭めなければならない**
> （＝原則B・原則C）

## 疑問9：自動リダイレクトなら検証不要、外部入力由来なら必要？

**当初の仮説**
> アプリケーションが自動的にリダイレクトする場合は検証不要。
> 外部入力によって遷移する場合に検証が必要。

**判定：ほぼ正しい。ただし「自動かどうか」は関係ない。**

`?next=` のリダイレクトも、ユーザーは何も操作せず**アプリが自動的に**飛ばしている。
動作としては完全に自動。それでも検証が要るのは、行き先の中身が外から来ているから。

**判断の軸は「誰が起動したか」ではなく「その行き先の文字列がどこで生まれたか」。**

| 遷移 | 行き先を決めるのは | 検証 |
|---|---|---|
| ログイン失敗 → `/login?error=1` | コード内の固定値 | 不要 |
| 記事投稿完了 → `/articles/{新規ID}` | サーバが作ったID | 不要 |
| `?next=` の値へ | **外部入力** | 必要 |
| Refererヘッダの値へ戻る | **外部入力** | 必要 |
| hidden フィールドの値へ | **外部入力**（改ざん可能） | 必要 |

**もう一点：外部入力の範囲を狭く見積もらない**（1-1の表を参照）。

### 最終形

> **リダイレクト先の文字列に、リクエスト由来の値が1文字でも混ざっているなら、
> その部分は検証が必要。**

「1文字でも」がポイント。`https://example.com/` + `外部入力` のように一部だけ混ぜる場合も対象。
だから「ホストは許可リスト側から取る」＝混ざる範囲をパスだけに限定する工夫が効く。

# 第6部 チェックリストと一般化

## 6-1. リダイレクトを実装するときのチェックリスト

```
□ 行き先の文字列に、リクエスト由来の値が混ざっているか？
   → 混ざっていない → 検証不要。ここで終わり
   → 混ざっている  → 以下へ

□ ① 混ぜない設計にできないか？（識別子・セッション）
□ ② 混ぜる範囲を最小にできないか？（パスだけ。ホストは固定値）
□ ③ 検証する場合：
   □ 部分一致（startsWith / endsWith / contains）を使っていないか
   □ 「削る」ではなく「拒否する」になっているか
   □ 検証した値そのものを使っているか（文字列に戻して再パースしていないか）
   □ scheme を https に限定しているか（javascript: 対策）
   □ 検証していないフィールドを素通ししていないか（userinfo 等）

□ サイト内の他の箇所に同じ穴がないか（OAuthの踏み台になる）
□ リダイレクト処理は1箇所に集約されているか
```

## 6-2. 同じ形をした他の脆弱性

**外部入力が「データ」ではなく「行き先や構造」を決めてしまう**と脆弱性になる。
だから対策も同じ順序になる。

| 脆弱性 | 外部入力が決めてしまうもの | ①混ぜない | ②範囲を絞る | ③検証 |
|---|---|---|---|---|
| オープンリダイレクト | 遷移先 | 識別子で受ける | 相対パスのみ | ホスト完全一致 |
| ディレクトリトラバーサル | ファイルパス | IDで受けて対応表 | basename のみ | 正規化して配下確認 |
| SQLインジェクション | SQL文の構造 | プレースホルダ | 列名は許可リスト | — |
| コマンドインジェクション | 実行コマンド | ライブラリで代替 | 引数を配列で渡す | 許可リスト |
| SSRF | リクエスト先 | 識別子で受ける | 内部IP帯を除外 | ホスト完全一致 |

## 6-3. 覚えておく3点

1. **外部入力の範囲を広く取る** — プロセスの外に一度出た値は全部そう
2. **秘密か / 書き換えられるか の2つを毎回問う** — 危険の種類が違えば対策も違う
3. **①混ぜない → ②範囲を絞る → ③検証する** の順で考える —
   検証が必要だと判断したら、まず①に戻れないか確認する
