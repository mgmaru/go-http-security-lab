# HTTP・REST・リソースの整理

## 1. はじめに

HTTPとRESTは似た文脈で登場するため混同しやすいですが、そもそも役割が異なります。

- **HTTP**：通信のためのルール（プロトコル）
- **REST**：APIをどのように設計するかという考え方（アーキテクチャスタイル）
- **リソース**：RESTにおいて、API上で識別して扱う対象・概念
- **Representation（表現）**：リソースをJSONやXMLなどの具体的なデータ形式で表したもの

まず全体像を図にすると、次のようになります。

```text
HTTP
│
├─ GET
├─ POST
├─ PUT
├─ PATCH
├─ DELETE
├─ Status Code
├─ Header
└─ Body
      │
      │ HTTPの仕組みを利用する
      ▼
REST
│
├─ リソース中心にAPIを設計する
├─ URIでリソースを識別する
└─ HTTPメソッドでリソースへの操作を表す
```

---

# 2. HTTPとは

HTTP（Hypertext Transfer Protocol）は、Web上でクライアントとサーバーが通信するためのルールです。

たとえば、次の通信はHTTPです。

```http
GET /users/123 HTTP/1.1
Host: example.com
```

HTTPでは、主に次のような仕組みが定義されています。

| 要素 | 役割 |
|---|---|
| GET / POST / PUT / DELETE など | どのような操作を要求するか |
| URI | どこに要求を送るか |
| Header | 通信に関する追加情報 |
| Body | 送受信するデータ本体 |
| Status Code | 処理結果を表す |

HTTP自体は、APIをどのようなURL構造で設計すべきかまでは決めていません。

---

# 3. RESTとは

REST（Representational State Transfer）は、Web上の対象を**リソース**として捉え、それらをHTTPの仕組みを使って操作する設計思想です。

たとえばユーザー管理APIなら、次のように設計できます。

```http
GET    /users/123
POST   /users
PUT    /users/123
DELETE /users/123
```

このとき、役割は次のように分かれています。

```text
GET /users/123
│       │
│       └─ 何を？ → ユーザー123というリソース
│
└─ どうする？ → 取得する
```

つまり、RESTでは基本的に次のように考えます。

```text
HTTPメソッド = どうするか
URI           = 何に対して行うか
```

---

# 4. 誤解①「HTTPメソッドを使えばRESTである」

## 誤解していた考え

> GETやPOSTなどのHTTPメソッドを使ってAPIを作ればREST APIである。

これは正確ではありません。

HTTPメソッドを使うだけなら、それは単に**HTTPを使ったAPI**です。

たとえば次のAPIもHTTPとしては成立します。

```http
POST /getUser
POST /createUser
POST /deleteUser
```

しかし、REST的な設計とは言いにくいです。

理由は、URLの中に操作（get / create / delete）が入り込んでいるからです。

RESTでは、対象と操作を分離します。

```http
GET    /users/123
POST   /users
DELETE /users/123
```

### 比較

| 設計 | URIが表すもの | 操作を表すもの | REST的か |
|---|---|---|---|
| `POST /getUser` | 操作まで含んでいる | URL + POST | あまりREST的ではない |
| `GET /users/123` | ユーザー123という対象 | GET | REST的 |

### 重要

**単にPOSTメソッドを使用しただけでは、RESTとは言えません。**

RESTでは、HTTPの仕組みを意味に沿って利用し、リソース中心にAPIを設計します。

---

# 5. リソースとは

RESTでいう**リソース（Resource）**は、簡単に言えば、

> **API上で名前を付け、識別し、操作の対象として扱うもの**

です。

たとえば、次のようなものをリソースとして考えられます。

- ユーザー
- 商品
- 注文
- 記事
- コメント
- 予約
- 検索結果
- 今日の天気
- ユーザー向けのおすすめ一覧

たとえば、

```text
/users/123
```

は、

> 「IDが123のユーザー」

というリソースを識別していると考えられます。

---

# 6. 誤解②「リソース = データ」

ここは特に注意が必要です。

## 誤解しやすい考え

```text
リソース = JSONデータ
```

と考えてしまうと、RESTの理解が少しずれてしまいます。

たとえば、

```http
GET /users/123
```

に対して、次のJSONが返ってきたとします。

```json
{
  "id": 123,
  "name": "Taro",
  "age": 28
}
```

この場合、

```text
「ユーザー123」
      ↓
   リソース

JSON
{
  "id": 123,
  "name": "Taro"
}
      ↓
リソースを表現したデータ
```

という関係です。

つまり、JSONそのものがリソースなのではありません。

---

# 7. リソースは「実体」より「概念・対象」に近い

今回の議論で特に重要だった点です。

リソースは、必ずしもデータベース上に物理的に存在する1行のデータとは限りません。

たとえば、

```text
/weather/tokyo/today
```

というAPIがあったとします。

これは、

> 「今日の東京の天気」

という対象をリソースとして扱っていると考えられます。

しかし、「今日の東京の天気」という1行がデータベースに保存されているとは限りません。

複数の観測データなどから、その都度計算して生成しているかもしれません。

同様に、

```text
/users/123/recommendations
```

なら、

> 「ユーザー123へのおすすめ一覧」

という概念的な対象をリソースとして扱えます。

したがって、リソースは

> **物理的なデータそのものというより、APIの世界で識別可能な対象・概念**

として考えると理解しやすくなります。

---

# 8. URIとリソースの関係

RESTでは、リソースをURIによって識別します。

```text
/users
```

→ ユーザーの集合

```text
/users/123
```

→ ユーザー123

```text
/products/50
```

→ 商品50

```text
/articles/10/comments
```

→ 記事10に紐づくコメントの集合

ここで大切なのは、URIは基本的に「操作」ではなく、**対象を表す**ということです。

```text
/users/123
    ↑
ユーザー123という対象
```

それに対して、HTTPメソッドで操作を指定します。

```text
GET    /users/123
PUT    /users/123
DELETE /users/123
```

---

# 9. ユーザー123には複数のデータが紐づく

「ユーザー123」というリソースには、当然さまざまなデータが関連します。

```text
ユーザー123
├─ 名前
├─ メールアドレス
├─ 年齢
├─ プロフィール画像
├─ 権限
├─ 注文履歴
└─ 投稿履歴
```

ここで、

```text
ユーザー123 = リソース
名前・メールアドレスなど = そのリソースに関するデータ
```

と考えることができます。

しかし、すべての関連データを毎回まとめて返す必要はありません。

たとえば、

```http
GET /users/123
```

では、

```json
{
  "id": 123,
  "name": "Taro",
  "email": "taro@example.com"
}
```

だけを返し、注文履歴は別のリソースとして、

```http
GET /users/123/orders
```

で取得することもできます。

```text
/users/123
    ↓
ユーザー123

/users/123/orders
    ↓
ユーザー123に紐づく注文一覧
```

---

# 10. 「紐づいたデータ」と「リソースの境界」は別問題

ここも重要です。

あるデータがユーザー123に紐づいているからといって、すべてを「ユーザー123という1つのリソース」に含める必要はありません。

たとえば、

```text
ユーザー123
├─ 基本情報
├─ 注文
├─ 投稿
└─ 通知
```

があった場合、APIでは次のように分けることができます。

```text
/users/123
/users/123/orders
/users/123/posts
/users/123/notifications
```

このように、

> **どこまでを1つのリソースとして扱うか**

はAPI設計上の判断になります。

したがって、

```text
データ同士が関連している
        ≠
必ず同じリソースとして扱う
```

という点に注意が必要です。

---

# 11. Representation（リソースの表現）

RESTの正式名称は、

> Representational State Transfer

です。

ここで重要なのが **Representation（表現）** です。

リソースそのものと、ネットワーク上でやり取りするデータは区別して考えます。

たとえば、ユーザー123という同じリソースでも、JSONで表現できます。

```json
{
  "id": 123,
  "name": "Taro"
}
```

XMLなら、次のように表現できます。

```xml
<user>
  <id>123</id>
  <name>Taro</name>
</user>
```

図にすると、

```text
                 ┌─ JSON
                 │
ユーザー123 ─────┼─ XML
（リソース）     │
                 └─ HTML

        同じ対象を異なる形式で表現できる
```

つまり、

```text
リソース
   ↓
API上で扱う対象・概念

Representation
   ↓
その対象をJSONなどで具体化した表現
```

という違いがあります。

---

# 12. 全体を1つの例で整理する

次のAPIを考えます。

```http
GET /users/123
```

これを分解すると、

```text
GET
│
└─ HTTPメソッド
   「取得する」という操作

/users/123
│
└─ URI
   「ユーザー123」というリソースを識別

↓ サーバーが処理

{
  "id": 123,
  "name": "Taro"
}
│
└─ Representation
   ユーザー123というリソースをJSONで表現
```

全体像は次のようになります。

```text
クライアント
    │
    │ GET /users/123
    │
    ▼
サーバー
    │
    │ 「ユーザー123」というリソースを取得
    │
    ▼
ユーザー123
（リソース）
    │
    │ JSONとして表現
    ▼
{
  "id": 123,
  "name": "Taro"
}
    │
    ▼
クライアント
```

# 13. 今回の誤解と修正後の理解

| 誤解・曖昧だった理解 | 修正後の理解 |
|---|---|
| HTTPとRESTは同じようなもの | HTTPは通信プロトコル、RESTはAPI設計思想 |
| HTTPメソッドを使えばREST | HTTPメソッドを使うだけではRESTとは限らない |
| POSTを使ったAPI = REST API | 単にPOSTを使うだけならHTTP APIでしかない場合もある |
| RESTはHTTPメソッドの使い分け | それだけでなく、リソース中心の設計が重要 |
| リソース = データ | リソースはAPI上で扱う対象・概念 |
| JSON = リソース | JSONはリソースのRepresentation（表現） |
| リソース = DBの1行 | DB上に物理的に存在しない概念もリソースになれる |
| 関連データは全部同じリソース | どこまでを1リソースとするかは設計次第 |

---

# 14. 最重要ポイント

今回の議論で、特に覚えておきたいポイントは次の4つです。

## ① HTTPとRESTは別の階層の概念

```text
HTTP = 通信するためのルール
REST = APIを設計するための考え方
```

## ② RESTは「対象」と「操作」を分ける

```text
GET /users/123
│       │
│       └─ 対象：ユーザー123
│
└─ 操作：取得
```

## ③ リソースはデータそのものではない

```text
リソース
= API上で識別して扱う対象・概念

JSON
= そのリソースを表現したデータ
```

## ④ リソースの境界はAPI設計上の判断

```text
/users/123
/users/123/orders
/users/123/posts
```

のように、関連するデータであっても別リソースとして切り出せます。

---

# 15. 一言でまとめる

```text
HTTP
= 「どう通信するか」のルール

REST
= 「HTTPを使ってAPIをどう設計するか」の考え方

リソース
= 「APIで何を対象として扱うか」

URI
= 「そのリソースをどう識別するか」

HTTPメソッド
= 「そのリソースに何をするか」

Representation
= 「そのリソースをどのようなデータとして表現するか」
```

この5つを分けて理解すると、REST APIの設計がかなり見通しよく理解できるようになります。
